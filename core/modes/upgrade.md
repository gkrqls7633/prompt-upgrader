# upgrade 모드

모호한 사용자 프롬프트나 지침을 고수준 프롬프트로 바꾼다. 프레임 어휘로 태도를 바꾸고, 정밀 어휘로 결과의 형태를 정한다.

## 읽을 파일

- `core/rubric.md`
- `core/vocabulary/precision/` 전체
- `core/vocabulary/frames/` 중 1단계에서 판별한 의도의 파일
- `core/rules/` 중 `applies_to`에 입력 종류(user_prompt 또는 instruction)가 있는 규칙

## 절차

### 1. 의도를 판별한다

| 의도 | 신호 | 프레임 파일 |
|---|---|---|
| 비판·검증 | 피드백, 검토, 괜찮은지, 문제점 | `frames/critique.md` |
| 아이디어 확장 | 아이디어, 기획, 브레인스토밍 | `frames/ideation.md` |
| 설명·학습 | 설명, 알려줘, 이해, 교육 | `frames/explain.md` |
| 의사결정 | A vs B, 뭐가 나아, 선택, 우선순위 | `frames/decision.md` |
| 작성·편집 | 다듬어, 고쳐 써, 퇴고, 메일, 공지 | `frames/edit.md` |
| 분석 | 왜, 원인, 분석, 지표 | `frames/analysis.md` |
| 고객 관점 | 사용자 입장, 고객, 이탈, UX | `frames/customer.md` |
| 실행 작업 | 수정, 변환, 이름 변경, 실행, 생성처럼 결과가 정해진 작업 | 없음 (프레임 추천 안 함) |

의도가 둘 이상이면 주된 의도 하나를 고르고, 다른 의도는 추천 이유에 적는다.

### 2. 대상 에이전트에 맞춘다

대상 에이전트의 지침이 함께 주어지면 그 에이전트의 담당 업무, 보유 도구, 출력 형식에 맞춰 개선본을 쓴다. 지침이 정한 범위 밖의 요청이면 그 사실을 알린다.

### 3. 빠진 정보를 묻는다

기본은 질문형이다. 목적, 입력 자료, 독자, 완료 기준 중 결과를 가장 크게 바꾸는 순서로 최대 3개를 묻는다. 가능하면 객관식 선택지를 붙인다. 이미 주어진 정보는 묻지 않는다.

입력에 `바로` 또는 `--quick`이 있으면 묻지 않고 진행한다. 이때 개선본 안의 채워야 할 빈칸은 `[대괄호]`로 표시하고, 개선본 아래에 "가정" 목록을 둔다.

### 4. 프레임 어휘를 추천한다

1단계 프레임 파일에서 1~3개를 고른다. 각각 왜 맞는지와 "쓰지 말 때"에 비춘 주의점을 한 줄씩 붙인다. 실행 작업이면 이 단계를 건너뛰고 "프레임 불필요: 결과가 정해진 실행 작업"이라고 쓴다.

질문형이면 질문과 함께 추천을 보여주고, 답을 받은 뒤 5단계로 간다.

### 5. 개선본을 만든다

1. 첫 번째 추천 프레임의 템플릿을 뼈대로 쓴다 (실행 작업이면 프레임 없이).
2. 정밀 어휘로 빈칸을 채운다: 행동(ACT), 범위(SCP), 독자(AUD), 형식(FMT), 완료(DON), 필요하면 근거(EVD).
3. 자료가 있으면 태그로 구분한다 (R-STR-001).
4. 금지 문장에는 이유를 붙인다 (R-CTX-002, R-EMP-002).
5. 개선본은 입력과 같은 언어로 쓴다.

### 6. 전후 점수를 매긴다

`core/rubric.md`의 사용자 프롬프트용(U1~U6)으로 원문과 개선본을 채점한다. 지침을 upgrade하면 지침용(I1~I8)을 쓴다.

원문이 이미 85점 이상이면 "큰 변경 불필요"라고 쓰고, 원문을 거의 그대로 둔 채 사소한 제안만 한다. 잘 쓴 프롬프트를 억지로 바꾸면 오히려 의도가 흐려진다.

## 출력 형식

질문형의 첫 응답:

````markdown
prompt-upgrader v1.0.0 · 규칙 기준일 2026-11-21

## 확인하고 싶은 것
1. 이 분석 결과는 어디에 쓰이나요? (a) 경영진 보고 (b) 팀 내부 공유 (c) 의사결정 회의
2. ...

## 추천 프레임 (답을 받은 뒤 적용)
- **F-ANL-03 가설 기반 분석**: 원인을 찾는 요청이고 데이터가 많아서. 주의: 가설을 세울 사전 지식이 없으면 MECE로 먼저 나눈다.

`바로`라고 답하면 지금 정보로 가정을 세워 진행합니다.
````

개선본 응답 (질문에 답한 뒤 또는 `바로`):

````markdown
prompt-upgrader v1.0.0 · 규칙 기준일 2026-11-21

## 추천 프레임
- **F-CRT-01 악마의 대변인**: 기획안의 약점을 찾는 것이 목적이라서. 주의: 장점은 다루지 않으므로 균형 평가가 필요하면 대안을 쓴다.

## 개선된 프롬프트
```text
(개선본 전문)
```

## 변경 요약 (원문 42점 → 개선본 91점)
| 변경 전 | 변경 후 | 근거 |
|---|---|---|
| 피드백해줘 | 허점 5개를 심각도 순으로 | V-SCP-03, R-OUT-003 |
| (없음) | 출시 후 1년 안에 실패한다고 가정 | F-CRT-01, V-SCP-05 |

## 가정
- (바로 모드에서만. 질문형에서는 이 절을 쓰지 않는다)

## 재검증 필요
- (90일이 지난 규칙·어휘 ID. 없으면 "없음")
````

- 첫 줄 머리말의 버전과 기준일은 `core/PROTOCOL.md`의 방법으로 만든다. 위의 값은 예시다.
- 개선본은 반드시 코드 블록 하나에 넣는다. 사용자가 그대로 복사해 쓰기 때문이다.
