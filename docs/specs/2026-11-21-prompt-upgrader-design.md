# prompt-upgrader 설계 스펙

- 작성일: 2026-11-21
- 상태: 사용자 검토 대기
- 대상 버전: v1.0.0

## 1. 목적

사내 에이전트 빌더(전사 마켓플레이스)에 등록된 에이전트의 **지침 품질을 검수**하고, 사용자가 에이전트에 입력하는 **모호한 프롬프트를 고수준 프롬프트로 변환**한다. 근거는 공식 프롬프트 엔지니어링 문서와 자체 평가 결과이며, 모델이 바뀌어도 규칙이 낡지 않도록 갱신 체계를 내장한다.

### 사용 장면
1. **지침 검수**: 에이전트 빌더에 등록된 에이전트 지침이 담당 업무와 보유 도구·스킬에 맞게 잘 쓰였는지 점수와 문제점으로 보여준다.
2. **사용자 프롬프트 고도화**: "보고서 써줘" 같은 입력을, 대상 에이전트의 맥락을 반영한 고수준 프롬프트로 바꾼다.

### 사용자
- 에이전트를 만드는 사람(빌더): 지침 검수
- 에이전트를 쓰는 사람(현업): 프롬프트 고도화
- 스킬 관리자: 갱신(refresh)과 평가(eval)

### 성공 기준
- 설치는 1분 이내, 사용은 명령 한 줄로 가능하다.
- 평가셋 기준 `must_flag` 검출률 90% 이상, `must_not_flag` 오탐 0건, 모범 프롬프트 점수 85점 이상.
- 모든 결과에 스킬 버전과 규칙 기준일이 표시되고, 90일이 넘은 규칙은 경고된다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| 지원 도구 | Claude Code 우선. Codex, Cursor, 붙여넣기용 범용 어댑터 제공 |
| 구조 | 도구 중립 코어(`core/`) + 얇은 어댑터. Claude Code용 `SKILL.md`는 루트에 둔다 |
| 대상 모델 | 공통 규칙 + Claude 전용 규칙(`scope` 태그로 구분). 다른 회사 규칙은 같은 형식으로 추후 확장 |
| 언어 | README와 설명은 한국어. 어휘는 한국어/영어 병기. 개선본은 입력 언어를 따른다 |
| 고도화 방식 | 질문형(빠진 정보 1~3개를 먼저 질문)이 기본. `바로`/`--quick`이면 가정을 명시하고 즉시 변환 |
| 갱신 | refresh 모드가 변경안을 제안하고, 사람이 승인하며, 평가를 통과해야 확정 |
| 저장소 | GitHub Public. 사내 정보는 넣지 않고 모든 예시는 가상의 에이전트로 작성 |
| 저작권 | 『AI 프롬프트 어휘 사전』의 목록이나 문구는 옮기지 않는다. 어휘는 공식 문서와 널리 알려진 방법론에서 새로 작성한다 |

## 4. 모드

| 모드 | 입력 | 출력 |
|---|---|---|
| `review` | 에이전트 지침. 선택: 담당 업무, 보유 도구·스킬 목록 | 총점과 항목별 점수, 문제 목록(규칙 ID, 원문 인용, 이유, 수정 제안), 재검증이 필요한 규칙 경고 |
| `upgrade` | 사용자 프롬프트 또는 지침. 선택: 대상 에이전트의 지침 | 질문 1~3개 → 개선본(코드 블록), 추천 프레임 어휘와 그 이유, 변경 요약표(전 → 후, 근거 ID), 남은 가정 |
| `refresh` | 선택: 기준 모델 ID | 기준선 평가, 문서 대조, 변경안 파일. 승인 전에는 규칙 파일을 수정하지 않는다 |
| `eval` | 선택: `cases`, `effects`, 모델 ID | 평가 결과 파일과 통과 여부 |

**모드를 지정하지 않으면** 입력을 보고 판단한다. 긴 지침이나 시스템 프롬프트로 보이면 `review`를 실행한 뒤 `upgrade` 여부를 묻는다. 짧은 사용자 요청이면 `upgrade`를 실행한다.

**결과 머리말**: 모든 결과의 첫 줄은 `prompt-upgrader v<VERSION> · 규칙 기준일 <가장 오래된 verified 날짜>`이다.

### upgrade 절차
1. 의도를 판별한다: 비판·검증, 아이디어 확장, 설명·학습, 의사결정, 작성·편집, 분석, 고객 관점, 실행 작업.
2. 대상 에이전트의 지침이 주어졌다면 그 역할과 도구에 맞춘다.
3. 빠진 정보(목적, 입력 자료, 독자, 완료 기준) 중 결과를 가장 크게 바꾸는 것을 1~3개 질문한다. `바로`면 이 단계를 건너뛰고 가정을 명시한다.
4. 프레임 어휘를 1~3개 추천하고, 각각 맞는 이유와 부작용을 붙인다. 프레임이 필요 없는 실행 작업이면 추천하지 않는다.
5. 프레임 어휘와 정밀 어휘로 개선본을 만든다.
6. 사용자 프롬프트 채점 기준으로 개선 전후 점수를 보여준다.

## 5. 규칙

### 형식
```markdown
### R-EMP-002  절대 금지어 대신 범위와 이유를 쓴다
- scope: common
- applies_to: instruction, user_prompt
- severity: high
- status: active
- source: S-01
- verified: 2026-11-21 / claude-fable-5-2, claude-haiku-5-5
- 검출 신호: NEVER, 절대, 무조건 + 이유 없음
- 고치는 법: 적용 범위를 좁히고 이유를 한 문장 붙인다
- Before: 파일을 절대 삭제하지 마.
- After: 파일을 삭제하기 전에는 승인을 받는다. 복구할 수 없는 작업이기 때문이다.
```
- `scope`: `common` | `claude` (추후 `openai`, `google` 등)
- `severity`: `high` | `medium` | `low`
- `status`: `active` | `deprecated`. deprecated에는 `deprecated_reason`과 `replaced_by`를 단다.

### 카테고리 (ID 접두어)
| 파일 | 접두어 | 다루는 것 |
|---|---|---|
| clarity | CLR | 행동 동사, 모호어, 기준을 숫자로 |
| context | CTX | 이유, 독자, 결과물의 쓰임 |
| structure | STR | XML 구역 나누기, 긴 자료의 위치, 예시 3~5개 |
| emphasis | EMP | 대문자 강조, 부정형 지시, 절대 금지어 |
| tools | TOL | 언제 쓰고 언제 안 쓰는지, 비용, 병렬 호출, 과잉 호출 문구 |
| boundaries | BND | 구체적인 승인 대상, 승인 없이 해도 되는 일 |
| completion | CMP | 완료 기준, 검증 방법, 검증하지 못한 것 보고 |
| output | OUT | 출력 형식 |
| agentic | AGT | 위임 기준, 보고, 조기 중단, 쌓인 낡은 지시 |
| fit | FIT | 지침과 담당 업무·보유 도구의 일치 (review 전용) |
| legacy | LEG | 구식 패턴: prefill, budget_tokens 등 (claude) |

v1 목표: 카테고리당 3~6개, 합계 약 45개.

## 6. 어휘집

### 정밀 어휘 (`vocabulary/precision/`)
모호함을 줄인다. 상황 9개: action(ACT), scope(SCP), audience(AUD), done(DON), format(FMT), reasoning(RSN), evidence(EVD), tools(TOL), delegation(DLG).

```markdown
## V-ACT-01  수정해 / Change
- 상황: 제안이 아니라 결과물을 직접 바꾸길 원할 때
- 약한 표현: "개선해줄 수 있어?", "한번 봐줘"
- 강한 표현: "이 함수를 응답 시간 200ms 이하가 되도록 수정해"
- 효과가 있는 이유: 질문형 요청은 제안만 돌아오고, 명령형은 실행으로 이어진다
- 업무 예시: (코딩 / 문서 / 데이터 / RAG 중 1~2개)
- verified: 2026-11-21 / claude-fable-5-2
```

### 프레임 어휘 (`vocabulary/frames/`)
모델의 기본 태도를 바꾼다. 의도 7개: 비판·검증(CRT), 아이디어 확장(IDE), 설명·학습(EXP), 의사결정(DEC), 작성·편집(EDT), 분석(ANL), 고객 관점(CUS).

```markdown
## F-CRT-01  악마의 대변인 / Devil's Advocate
- 의도: 비판, 검증
- 바뀌는 태도: 칭찬 위주의 무난한 조언 → 반대 논리로 허점을 집요하게 공격
- 쓸 때: 기획안, 제안서, 의사결정 직전 검증
- 쓰지 말 때: 균형 잡힌 평가가 필요할 때
- 대안: "장점 3개를 먼저 짚고, 그다음 악마의 대변인으로 공격해"
- 함께 쓸 정밀 어휘: V-SCP(관점 지정), V-FMT(개수, 심각도 순), V-DON(검증 방법)
- 템플릿: 너는 이제부터 악마의 대변인이다. [대상]이 [실패 조건]이라고 가정하고 ...
- Before / After
- 효과 평가: evals/effects/E-01
- verified: 2026-11-21 / claude-fable-5-2
```

v1 후보(의도별 2~4개, 합계 약 20개): 악마의 대변인, 프리모템, 레드팀, 회의적인 투자자 / 제1원리 사고, 역발상, "Yes, and" 조력자 / 소크라테스식 질문, 파인만 기법, 비전공 신입 독자 / 스틸맨, 결정 매트릭스, 기회비용 관점 / 깐깐한 편집장, 첫 문장만 읽는 바쁜 임원 / 5 Whys, MECE, 가설 기반 분석 / 까다로운 실사용자, 이탈 직전 고객.

정밀 어휘 v1 목표: 상황당 4~6개, 합계 약 45개.

## 7. 채점 기준 (`core/rubric.md`)

**에이전트 지침용 (100점)**: 역할·미션·이유 15, 도메인 판단 기준 15, 도구·스킬 사용 지침 15, 완료 기준과 검증 15, 경계와 승인 10, 작업 절차 10, 출력 형식 10, 표현 품질 10.

**사용자 프롬프트용 (100점)**: 목표와 행동 20, 맥락과 이유 20, 입력 자료 15, 범위와 제약 15, 출력 형식과 독자 15, 완료 기준 15.

**등급**: 90점 이상은 바로 사용, 70~89점은 개선 권장, 70점 미만은 재작성.

**채점 원칙**: 감점할 때는 원문 구절을 인용하고 규칙 ID를 단다. 인용할 구절이 없으면(정보가 빠진 경우) "누락"이라고 쓰고 어떤 정보가 빠졌는지 적는다. 도메인에 따라 해당이 없는 항목은 만점으로 처리하고 "해당 없음"이라고 표시한다.

## 8. 근거 문서 (`core/sources.md`)

```markdown
## S-01  Claude prompting best practices
- url: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices.md
- scope: claude
- 근거로 쓰는 규칙: R-EMP-001, R-EMP-002, R-TOL-003, R-LEG-001
- last_checked: 2026-11-21
- 핵심 주장 스냅샷:
  - 강한 강조어(CRITICAL, MUST)는 최신 모델에서 과잉 호출을 유발 → R-TOL-003
  - 마지막 assistant 턴 prefill은 400 에러 → R-LEG-001
  - 긴 자료는 위에, 질문은 끝에 → R-STR-004
```
v1 출처는 Anthropic 공식 문서 4~6개(개요, 모범 사례, 모델별 가이드)다. `common` 규칙은 특정 모델에 의존하지 않는 일반 원칙으로 한정하고, 근거 문서를 1개 이상 단다.

## 9. 평가 (`evals/`)

### 검출 평가 (`cases/`, 18개)
```markdown
## C-07  모호한 데이터 분석 요청
- mode: upgrade
- input: 지난달 매출 데이터 분석해줘
- must_flag: R-CLR-001, R-CTX-001, R-OUT-001, R-CMP-001
- must_not_flag: R-LEG-*
- expect: 질문에 '분석 목적'이나 '독자'가 포함됨. 개선본에 출력 형식이 지정됨
```
구성: 업무 유형 4가지(코딩, 문서, 데이터, RAG) × 사용 장면 2가지(지침, 사용자 프롬프트) = 8개, 프레임 어휘 추천 6개, 이미 잘 쓴 프롬프트 2개(오탐 검사), 구식 패턴 2개.

**통과 기준**: `must_flag` 검출률 90% 이상, `must_not_flag` 오탐 0건, 잘 쓴 프롬프트 점수 85점 이상, 프레임 추천 케이스에서 기대 프레임이 추천 목록에 포함.

### 효과 평가 (`effects/`, 10쌍)
같은 요청을 어휘 없이(A) 한 번, 어휘를 넣고(B) 한 번 실행한다. 판정 기준을 미리 적어두고, B가 기준을 더 많이 충족하는지 본다.
```markdown
## E-01  악마의 대변인 (F-CRT-01)
- A: 직장인 대상 명상 앱을 기획했어. 구독료 월 1만원, 아침 5분 오디오. 이 기획안 어때? 피드백해줘.
- B: (F-CRT-01 템플릿을 적용한 프롬프트)
- 판정 기준:
  1. 치명적 허점을 3개 이상 지적했는가
  2. 칭찬·장점 문장이 전체의 20% 이하인가
  3. 각 허점에 구체적 근거(가격, 경쟁, 지속 사용률 등)가 있는가
- 효과 있음: B가 A보다 판정 기준을 2개 이상 더 충족
```
구성: 프레임 어휘 6개, 핵심 정밀 어휘 4개.
**판정**: B가 A 대비 효과가 없으면 해당 어휘 항목에 `effect: none (<모델>, <날짜>)`을 기록하고 refresh에서 수정 또는 폐기 후보로 올린다.

### 실행과 기록
- `eval` 모드가 `evals/RUN.md` 절차를 따른다.
- 결과는 `evals/results/<YYYY-MM-DD>-<모델ID>-<baseline|after|manual>.md`에 저장한다.
- 효과 평가의 판정은 실행 모델이 아닌 별도 판정 단계(같은 세션의 별도 서브에이전트, 또는 사람)가 기준표로 채점한다. 실행 모델이 자기 출력을 채점하지 않게 하기 위해서다. 서브에이전트를 쓸 수 없는 도구에서는 판정을 사람이 한다.

## 10. 버전업 체계

### 버전 규칙 (SemVer)
| 변경 | 버전 | 예 |
|---|---|---|
| MAJOR | 호환이 깨짐 | 모드 추가·삭제, 출력 형식이나 채점 구조 변경 |
| MINOR | 내용 추가 | 규칙이나 어휘 추가, 평가 케이스 추가 |
| PATCH | 다듬기 | 문구 수정, `verified` 날짜 갱신 |

### 규칙과 어휘의 수명
- 삭제하지 않고 `deprecated`로 바꾸고 이유와 대체 ID를 남긴다. 다음 MAJOR 버전에서 삭제한다.
- `verified` 날짜가 90일을 넘은 항목이 결과에 쓰이면, 결과 하단에 "재검증 필요" 목록으로 표시한다.

### 갱신 시점
- 분기마다 첫 주
- 새 모델이 출시됐을 때 (회사가 쓰는 모델이 바뀔 때)
- 평가 점수가 통과 기준 아래로 떨어졌을 때
- 결과 하단에 재검증 경고가 자주 보일 때

### refresh 판정
문서 변화와 실제 효과, 두 신호를 함께 본다.

| 문서 | 평가 | 판정 |
|---|---|---|
| 변화 없음 | 통과 | 유지. `verified` 날짜만 갱신 (PATCH) |
| 규칙과 충돌하는 변화 | - | 수정 또는 폐기 후보 |
| 새 권고 | - | 신규 후보 |
| 변화 없음 | 효과 없음 | 수정 또는 폐기 후보 |

## 11. refresh 실행 런북 (MAINTAINING.md에 그대로 수록)

예상 소요 시간은 30~60분이고, 그중 사람이 개입하는 시간은 약 15분이다. 단계마다 **[담당]**을 표시한다.

### 0단계. 준비 [사람]
```bash
cd ~/Desktop/study/prompt-upgrader
```
```bash
git checkout main && git pull
```
```bash
git checkout -b refresh/2027-q1
```
브랜치 이름은 `refresh/<연도>-q<분기>` 또는 `refresh/<모델ID>` 형식으로 한다.

### 1단계. refresh 시작 [사람 → 에이전트]
Claude Code에서 다음을 입력한다.
```
/prompt-upgrader refresh
```
특정 모델 기준으로 돌릴 때:
```
/prompt-upgrader refresh --model claude-opus-5-5
```
Codex나 Cursor처럼 슬래시 명령이 없는 도구에서는:
```
core/modes/refresh.md 절차대로 refresh를 실행해줘. 기준 모델은 claude-opus-5-5야.
```
웹 문서를 읽을 수 있어야 하므로 웹 접근이 되는 도구에서 실행한다.

### 2단계. 기준선 평가와 문서 대조 [에이전트]
에이전트가 수행하고 결과 파일을 만든다. 이 단계에서는 규칙 파일을 수정하지 않는다.
1. 현재 규칙으로 평가 실행 → `evals/results/<날짜>-<모델>-baseline.md`
2. `sources.md`의 문서를 다시 읽고 스냅샷과 비교
3. 변경안 작성 → `refresh/<날짜>-proposal.md`

변경안 파일 형식:
```markdown
# refresh 변경안 2027-01-05 (기준 모델: claude-opus-5-5)
기준선: 검출률 94%, 오탐 0, 모범 점수 88, 효과 있음 9/10

| ID | 대상 | 판정 | 근거 |
|---|---|---|---|
| P-01 | R-TOL-003 | 수정 | S-01 문서 변경: "..." (인용) |
| P-02 | F-CRT-01 | 수정 | E-01 효과 없음 (A/B 판정 기준 차이 0) |
| P-03 | (신규) R-AGT-007 | 신규 | S-03 새 권고: "..." |
| P-04 | 나머지 41개 | 유지 | 변화 없음, 평가 통과 |

## P-01 상세
(변경 전/후 diff)
```

### 3단계. 변경안 검토와 승인 [사람]
`refresh/<날짜>-proposal.md`를 읽고 채팅으로 항목별 결정을 알려준다.
```
P-01, P-03 승인. P-02는 보류.
```
- 승인: 반영한다.
- 보류: 이번에는 반영하지 않고 변경안 파일에 보류로 기록한다.
- 거절: 반영하지 않고 이유를 기록한다.

검토할 때 확인할 것: 근거 인용이 실제 문서에 있는지(링크를 열어 확인), 변경이 사내 사용 방식과 충돌하지 않는지.

### 4단계. 적용과 재평가 [에이전트]
1. 승인된 항목만 규칙과 어휘 파일에 반영한다.
2. 평가를 다시 실행한다 → `evals/results/<날짜>-<모델>-after.md`
3. 기준선과 비교표를 보여준다. 통과 기준을 지키지 못하거나 기준선보다 나빠진 지표가 있으면, 원인이 된 항목을 되돌리고 보고한다.

### 5단계. 확정 [사람 → 에이전트]
비교표를 확인한 뒤 입력한다.
```
확정해줘
```
에이전트가 `VERSION`, `CHANGELOG.md`, `sources.md`의 스냅샷과 `last_checked`, 유지된 항목의 `verified` 날짜를 갱신한다.

### 6단계. 커밋과 공유 [사람]
```bash
git add -A
```
```bash
git commit -m "refresh: 2027-Q1 (claude-opus-5-5) v1.1.0"
```
```bash
git push -u origin refresh/2027-q1
```
GitHub에서 PR을 열고 main에 머지한다. 사내 사용자에게는 CHANGELOG의 해당 버전 항목을 공유한다.

### 중간에 멈췄을 때
- 2단계에서 멈춤: 아무 파일도 바뀌지 않았으므로 1단계부터 다시 실행한다.
- 4단계에서 멈춤: `git diff`로 반영 상태를 확인하고, 다시 하려면 `git checkout -- core/`로 되돌린 뒤 3단계의 승인 메시지를 다시 보낸다.
